# 阶段 10：跑满验证 + 水位控制（从"8 个"到"250 个"）

## 背景思考

用户质疑：之前测试池子只有 8 个，连 all 都填不满，是不是没检验所有源？
真相：源都跑了（8 个全跑），但**免费源可用率只有 ~1%**，压小抓取量时自然填不满。
用户拍板：加大抓取量直接跑满，不计时间成本，跑通是第一要务。

## 完成内容

### 分批验证（防卡死的关键修复）
- `Checker.check_all` 原来把全部代理一次 `asyncio.gather` 并发 —— 几万代理会打爆
  连接/内存。新增 **分批并发**：每批 `CHECK_BATCH_SIZE=500`，批内并发、批间串行。
- 新增 `on_batch` 回调参数，大批量验证时每批打进度日志，避免"看起来卡死"。

### 水位控制（目标驱动补源）
- `config/services.py`：定义服务与下限 `SERVICE_MIN`（cn/global × all/safe/stable），
  区域+安全双层下限。
- `ProxyService.service_levels()` 读各服务水位；`below_waterline()` 列缺口；
  `ensure_waterlines()` 循环补源直到达标或连续 N 轮无新增（源耗尽）停止。
- `RedisPool.count_by_region()` 按区域+安全/稳定子条件统计。
- 调度器改为**水位触发**：`make_waterline_job` 定期检查，低于下限就补源；
  `make_check_job` 复核淘汰。

### 全量跑通（真实数据）
- `scripts/full_ref.py`：全量抓取（不限每源量）→ 分批验证 → 一次性入库。
- 真实结果：
  ```
  总候选 28,588 → 可用 250 (0.9%)，耗时 26 分钟
  池子 {total: 250, https: 94, cn: 4, global: 246}
  ```
- `scripts/full_check.py`：复核+打安全标签。复核后 250 维持，
  匿名性 elite=3 / transparent=26 / 空=221，safe=3。

## 技术决策及理由

1. **分批串行**：单批 500 并发是经验值，够快又不爆连接。几万代理必须分批。
2. **验证完一次性入库**（脚本内）：全量跑通场景，先全部验证完再 put，
   避免逐批 put 的 Redis 抖动；也便于展示最终池子。
3. **探针关在跑满时**：探针给每个活代理加 2 次慢请求，26 分钟里大部分时间
   耗在等死代理超时。跑满用 probe_safety=False 快填池，安全标签由 check_pool 补打。
4. **水位触发而非定时抓**：定时抓是"不管缺不缺都抓"；水位是"缺才补，
   补齐停"，符合用户"按服务持续供应"的目标。

## 实际命令

```bash
# 全量跑满（后台）
setsid bash -c 'cd /mnt/f/桌面/PROJECT/proxy-pool && \
  PYTHONPATH=. nohup .venv/bin/python scripts/full_ref.py > fill.log 2>&1 < /dev/null'

# 复核 + 打安全标签
setsid bash -c 'cd /mnt/f/桌面/PROJECT/proxy-pool && \
  PYTHONPATH=. nohup .venv/bin/python scripts/full_check.py > check.log 2>&1 < /dev/null'
```

## 踩坑记录

- **坑 1**：`setsid` 不能直接接 `PYTHONPATH=... env` 前缀 → 必须包 `bash -c`。
- **坑 2**：shell 工具的 120s 超时会连带杀掉前台起的后台进程 → 必须 `setsid + disown`。
- **坑 3**：大批量验证无进度输出 → 误判卡死。加 `on_batch` 每批打日志。
- **坑 4**：探针（ipify/example）同步阻塞拖慢每批 28s → 跑满时关探针。

## 关键结论

- 免费源**可用率 ~1%**，但量大仍能堆出实货（250 个）。
- **国内代理稀缺**（250 里只有 4 个 CN）—— 免费源里国内活的最少。
- **safe 极难达标**（只有 3 个）：免费代理绝大多数透明（泄露真实 IP）。
- 系统从"定时抓一批"升级为"目标驱动补水"，池子有了真实库存。
