# 阶段 05：入库流程 + 调度器

## 背景思考

之前"抓→验→入库"是手动在 learn 脚本里串的，缺少两个东西让它变成"自动运转的池子"：
1. **入库流程**：首次入库（raw）要"只放可用且不重复"；池内复核（use）要"淘汰失效"。
2. **调度器**：不能靠人每隔几分钟手点一次，要定时自动跑。

## 完成内容

- `handler/proxy_service.py`：`ProxyService` —— 池子的门面服务，组合底层组件
  - `refresh()`：抓一批新代理 → 并发验证 → **首次入库**（只放 last_status 为真
    且池里还不存在的代理，返回 (新增数, 可用数)）。
  - `check_pool()`：取出池内全部代理 → 并发验证 → **逐个体检**：
    通过 → 写回；失败超 `MAX_FAIL_COUNT` → 删除淘汰；失败未超 → 写回再给机会。
    返回 (复核数, 淘汰数)。
  - 构造函数支持注入 fetcher/checker/pool（依赖注入），测试可换假组件。
- `helper/scheduler.py`：APScheduler 调度器
  - `make_refresh_job(service)` / `make_check_job(service)`：两个任务闭包，注入 service 便于测试。
  - `run_scheduler()`：每 5 分钟抓取（refresh），每 2 分钟复核（check_pool）。
- `tests/test_proxy_service.py`：用假 checker（控制哪些代理通过）+ 假 pool（内存字典）
  验证 check_pool 的淘汰逻辑（活的保留 / 没超阈值给机会 / 超阈值删除）。
- `tests/test_scheduler.py`：验证两个 job 闭包能触发对应 service 方法。

## 技术决策及理由

- **依赖注入而非硬编码**：`ProxyService.__init__` 允许传假组件。测试因此不用连
  Redis、不用真发网络请求，稳定且快。这也是"可测试性"的经典手段。
- **两阶段入库（raw / use）**：抓新代理（raw）和复核旧代理（use）是两件事，
  分开两个方法。raw 只关心"放进不重复的可用代理"，use 只关心"淘汰失效的"，
  职责单一、互不纠缠。
- **APScheduler interval 触发**：比 cron 简单直观，适合"每隔 N 分钟"这种节奏。
- **淘汰给缓冲**：失败一次不马上删，超阈值才删（参考之前策略：MAX_FAIL_COUNT=3）。
