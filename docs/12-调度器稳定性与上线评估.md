# 阶段 12：调度器稳定性修复 + 上线就绪评估

## 背景思考

阶段 11 交付后用户要"把服务起起来,看今天能否稳定提供 IP"。实际部署时暴露
一个隐蔽但致命的稳定性问题:**补源 job 无限跑、霸占调度器单实例,把复核 job 挤掉**。
同时"cn 供应不足"要不要作为硬性要求,直接决定了补源 job 是否会陷入死循环。

## 定位的根因

调度器日志反复出现:
```
waterline_job ... skipped: maximum number of running instances reached (1)
```
APScheduler 默认 `max_instances=1`:一个 job 实例还在跑,下一次触发就被跳过。

**为什么 waterline job 一直占着不退出?** 看 `ensure_waterlines` 的循环:

```
while below_waterline(levels):
    added, _ = refresh(...)     # 每轮全源刷新
    if added == 0: stalls(); if stalls>=3: break
    ...
```

只要"每轮都能新增代理",`added>0` 就让 `stalls` 清零、循环继续。而现实里:
- **cn 的 all/safe/min 下限(30/5/…)永远达不到**(免费 CN 源近乎全假),
  所以 `below_waterline` 永远有 cn 缺口 → 循环永不退出。
- 一条 refresh 要跑几十秒~几分钟(几万个候选分批验证),累积成一个
  **长达十几分钟的补源 job**,占满调度器全部实例余量。

于是:复核 job(每 1 分钟)被 waterline 长期挤掉 → 新入库的死代理无人复核
→ cn 池子里囤一堆 score=0 的假端口 → API `need=cn` 返回的全是连不上的 IP。
这解释了"cn 看起来很满(70个)但一测全死"。

## 修复内容

### 1. cn 降级为"不设硬下限"(用户决策)
`config/services.py`:`SERVICE_MIN` 里 cn 的 all/safe/stable1/2/3 全部
`0`。用户明确:"cn 供应不足就供应不足,后面不做硬性要求,重点是系统稳定。"
→ `below_waterline` 对 cn 恒为假,补源 job 不再为追 cn 无限循环。
取用接口 `need=cn` 保留:池里有就给,没有就 404,诚实交付。

### 2. 补源总轮次硬上限(`config/services.py`)
新增 `MAX_WATERLINE_ROUNDS = 4`,`ensure_waterlines` 增加 `max_rounds` 参数,
循环里 `if rounds >= max_rounds: break`。与 `MAX_STALL_ROUNDS`(无新增 3 轮停)
组成**双保险**:
- 无新增 → stall 3 轮停
- 每轮都有新增 → 跑满 4 轮必停

这样即便某服务持续有货,单次补源 job 也最多跑 4 轮就退出,把调度器交还给
复核,绝不长期霸占单实例。

### 3. 结果(实测)
修复后调度器日志(带 `-u` 强制刷屏):
```
>> 水位检查触发
   所有服务达标(补源 0 轮)      # global 达标,立即收尾,不再无限追 cn
   池子 {'total':110, 'global':108, ...}
>> 复核任务触发                   # 每 1 分钟稳定触发,不再被挤掉
   复核 110 个,淘汰 3,池子 ...
```
- waterline job(cn 解除硬性后 global 达标)→ 每次触发 0 轮即退出,几乎零开销。
- 复核 job 恢复每 1 分钟稳定执行,死代理持续被清。

## 上线就绪评估(结论)

**可上线(cn 除外),关键证据:**

| 检查项 | 结果 |
|---|---|
| 交付 IP 真实可用 | ✅ 走代理访问 ipify 返回正常 IP(真转发),global 各档位 30/30 连通 |
| API 取用 | ✅ any/global/https/strict/stable3 30/30 返回 200 |
| 调度器稳定性 | ✅ waterline 达标即退,复核每 1min 稳定跑,不阻塞 |
| Redis 持久化 | ✅ RDB 快照默认开启(save 900/300/60),重启不丢池子 |
| 池子健康度 | global ~100-110,stable3 ~98,safe ~27,水位全达标 |
| 进程守护 | ⚠️ 目前手动 setsid 后台跑,无自动拉起 |

**上线前仍要做(风险点):**
1. **进程黑(没有 supervisor/systemd/PM2 守护)**——目前靠手动 setsid,
   进程崩了没人拉。上线必须套进程管理(systemd unit 或 supervisor)。
2. **Flask 用的 debug 模式**(reload 开销+不安全),上线应 `debug=False` +
   gunicorn 多 worker 跑,以免单 worker 阻塞时 API 卡死。
3. cn 池实际只有 1-2 个、且多为假端口短命死货,`need=cn` 交付质量不保
   (用户已接受,不计入上线阻塞)。

## 踩坑记录

- **坑 1**:`ensure_waterlines` 的 `while` 在"每轮都有新增"时无穷尽——
  光有 `MAX_STALL_ROUNDS` 不够。`MAX_WATERLINE_ROUNDS` 补上后双保险才稳。
- **坑 2**:根因居然不是某个 bug,而是**配置(硬性下限)与源现实(CN 空位)的
  冲突**。把不可达目标从判定中剔除(降为 0)即解。
- **坑 3**:调度器日志用 `-u` 才不缓冲;否则 `print` 滞后落盘,看不出 job 效果。
