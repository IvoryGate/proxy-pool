# 阶段 16：多页抓取 + 国内池恢复 + 脏 IP 拦截

## 背景思考

网关（poverty-gateway）反馈补源"不涨量"：水位目标 global 1000，但池子长期
卡在 130-180。起初怀疑补源参数（轮数/每源抓取量），实测一轮 refresh 发现
候选 2495 个里两轮重叠 2455（98.4% 重复）——**补源在同几批 IP 上打转**。

根因拆解：
1. **静态源占 90% 候选且低频更新**（monosans/jetkai/thespeedx 等 GitHub
   列表，更新周期小时级~天级），每次抓内容基本一致。
2. **动态源只抓固定 1 页**：ip89 只抓 `index_1.html`、kuaidaili 默认
   `page_count=1`、scdn 只 `page=1`——多页的新 IP 全浪费。
3. **cn 水位全为 0**：补源循环只追 global，国内源（ip89/ip3366 等活跃源）
   抓到的新 IP 复核淘汰后没人补，国内池持续缩水。

另外确认：网关/zen 探测本就不分区域（快照里已有国内 IP 在跑 zen），
只要 IP 能发通 + 稳定 + https + 低延迟即可用。所以恢复国内池是合理的。

## 完成内容

1. **ip89 多页**：`page_count=3`，抓 `index_1..3.html`（每页 ~40 个），
   候选 40 → 70。
2. **kuaidaili 多页**：默认 `page_count=1→3`（inha/intr 两类型 × 3 页），
   候选 24 → 72。
3. **scdn 多页**：`page_count=3`（per_page=100），候选 100 → 300。
4. **cn 水位恢复**：config/services.py 中 cn 从全 0 改为
   `all=100 / stable1=30 / stable2=10 / stable3=5`，让补源循环维护国内池。
5. **脏 IP 拦截**：新增 `_valid_ipv4()`——拦截带前导零的脏 IP
   （`141.000.11.253`）。实测多页抓取后候选量暴增，暴露出这类 IP 会让
   httpx 构造代理 URL 时抛 `InvalidURL` 崩溃整个验证批次（asyncio.gather
   直接炸，补源 job 中断）。
6. **补源周期适配**：`WATERLINE_INTERVAL 3→5` 分钟。多页后单轮 refresh
   耗时显著上升（候选翻倍、验证更久），3 分钟周期内 2 轮跑不完导致
   APScheduler `job skipped: maximum running instances reached`，
   补源频率反而下降。放宽到 5 分钟，2 轮补源有充足时间，复核仍 1 分钟兜底。

## 技术决策及理由

- **多页抓取选 3 页而非全量**：页数越多验证负担越重，而免费源通过率
  ~1%，边际收益递减。3 页是量/质折中，后续可观察再调。
- **`_valid_ipv4` 放 helper/check.py 而非 util**：它在验证环节用，
  check.py 的 `_format_check` 是唯一入口；proxy_service 预筛处也复用它，
  双重保险（预筛 + 逐条验证都拦）。
- **cn 水位设保守值**：国内免费代理 https 通过率低、寿命短，目标不宜
  追高（all=100 已是尽力），避免补源循环被 cn 卡死反复空转。

## 踩坑记录

1. **`docker inspect` 的 Mounts 为空**：compose 用 build 而非 volume 挂载，
   改代码必须 rebuild，不能只改宿主机文件。
2. **容器内测试读到旧代码**：直接 `docker exec ... python` 用的是容器内
   COPY 的代码，要测宿主机改动必须 `-v` 挂载或 rebuild。
3. **`asyncio.run` 的 gather 内异常不会优雅返回**：一个脏 IP 让整个验证
   批次崩溃、补源 job 直接抛异常中断。用 `_valid_ipv4` 在发请求前拦死。
4. **补源提速的副作用**：候选翻倍后单轮 75s→150s+，3 分钟周期装不下
   2 轮，job 被 APScheduler skip。放宽周期比砍抓取量更划算（复核频率不变）。

## 下一步

- 观察池子：多页抓取 + cn 水位生效后，cn 从 2 → 33~39 并稳定；总量
  104 → 160+。持续观察是否突破之前 130-180 的平台期。
- 网关侧联动：网关 zenhit 正分只有 19 个，多页新增的候选需网关补池
  重新探测才会被选中。若网关可用数仍低，可考虑调高网关 `PROBE_BATCH`/
  `PROBE_CONCURRENCY`。
- 若 global 长期补不满 1000，评估调低到现实值（400-500）。
