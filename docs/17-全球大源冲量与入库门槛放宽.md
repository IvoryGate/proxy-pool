# 阶段 17：全球大源冲量 + 放宽入库门槛 + fd 修复（池子 160 → 2000+）

## 背景思考

阶段 16 后池子稳定在 300-355（global ~310），用户仍要冲 global 1000。
此前判断"免费源稳态容量 ~325 是瓶颈"，但用户坚持继续挖。本阶段核心矛盾：
**补源每轮入库 ~67（转化率极低），池子卡在 300-350 上不去**。

拆解瓶颈：
1. **候选总量不足**：已有 20 源合格候选基本挖尽，缺"冲量型"超大源。
2. **入库门槛双重验证过严**：入库要求 `ipify 存活 + baidu 真实转发` 双过。
   实测单轮 ipify 通过 1133，但 baidu 再砍一刀只剩 67 入库 —— **baidu 是
   拦路虎**。但我们的场景是网关转发到 opencode，不是访问 baidu。
3. **并发调优踩坑**：把验证并发 500→1500 想冲吞吐，结果触发容器 fd 上限
   （默认 1024），`OSError: Too many open files` 让复核整批误杀，池子从
   1200 一路崩到 550。

### 差异化配额机制（max_items）
`fetcher/base.py` 声明 `max_items = None` 属性；`fetcher/manager.py` 沿 MRO
找第一个声明者（非 BaseFetcher 才算"声明过"）：
- 声明了 → 用源值（高质源放开 None、冲量源设大、死源降权 50）
- 未声明 → 用全局 `MAX_PER_SOURCE=250`

### 放宽入库门槛（关键突破）
`helper/check.py` 的 `_check_one_async`：**baidu 真实转发不再作为入库/淘汰
硬门槛**。理由：
- ipify 回显已验证"流量真经过代理"（目标看到的是代理出口 IP），足以拦截
  劫持/伪代理。
- baidu 砍掉 95% 入库量（1133 通过 → 67 入库），但场景是网关转发到
  opencode，不是访问 baidu。
- 最终质量交给网关 zen 探测把关（不达标的进不了网关可用池）。

效果：单轮 refresh 入库 **67 → 938（14 倍）**。

### 调度周期修正
`helper/scheduler.py`：`WATERLINE_INTERVAL` 3→5→8 分钟；`config/services.py`
`MAX_WATERLINE_ROUNDS 2→1`。适配单轮 refresh ~235s（接入大源后更久），
8 分钟周期固定 1 轮绝不 skip（此前 2 轮出现 job skip，补源被跳过导致池子
净流出）。水位/复核任务加异常捕获 + `flush=True`，异常不再静默吞掉。

### fd 上限修复
`docker-compose.yml` scheduler 加 `ulimits.nofile: 65535`。容器默认 fd 1024，
500 并发验证 × 每代理多连接（ipify+baidu+https）会超限。`CHECK_BATCH_SIZE`
回滚到 500（1500 虽吞吐更高但爆 fd 后误杀代价远大于收益）。

## 技术决策及理由

- **放宽 baidu 而非删除**：`_reality_ok` 仍保留调用（能到真实站拿 https
  能力探测），只是结果不再决定生死。质量下限由 ipify + 网关 zen 双重兜底。
- **冲量选 SoliSpirit 15000 而非全量**：134k 全量验证单轮要 1.5h+，远超
  8 分钟周期；15000 × 4.4% ≈ 660 潜在入库已足够每轮净增几百。
- **fd 提到 65535 而非降并发到 300**：并发 500 是吞吐/稳定性平衡点，
  提 fd 是零成本根治。

## 踩坑记录

1. **并发 500→1500 爆 fd**：`OSError: [Errno 24] Too many open files`，
   asyncio.gather 抛出导致验证整批中断，复核把活代理当死删（1200→550）。
   症状"池子莫名大额下跌 + 日志无异常"极隐蔽。排查靠 `docker logs` 尾部
   的 traceback。
2. **APScheduler job skip 无感**：8 分钟周期内上一轮补源没跑完，下轮触发
   `maximum running instances reached` 被跳过，池子持续净流出但日志只在
   grep skip 时可见。
3. **stdout 缓冲**：补源 400s+ 的 print 被 Python 缓冲，日志看起来"水位触发
   后无输出"，误判为补源没跑。加 `flush=True` 解决。
4. **大额复核淘汰 96/161/210 误判**：之前怀疑是代理真死，实为验证目标
   瞬时限流/并发爆 fd 的整批误杀。本轮用 fd 修复根治，复核恢复小额淘汰。

## 成果

- proxy-pool 池子：**160 → 稳定 2000+**（global 稳定 1100-2000 区间）。
- 网关真实对话验证通过（`nemotron-3-ultra-lite` 正常回复）。
- 单轮入库转化率 14 倍提升。
