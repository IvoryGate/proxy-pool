# 阶段 21：验证吞吐与目标可达性优化

## 背景思考

网关侧反馈「几乎没可用代理」：proxy-pool `/count` 看着还有 160+ 个、https 40+
个，但网关拿去做 zen 探测后只剩个位数。排查后发现，问题不全是上游 free 档
封 IP，代理池自己也在制造瓶颈：

1. **https 标记验证的不是业务目标**：`HTTPS_URL` 一直是
   `https://ip.3322.net`。代理能 CONNECT 到 3322，不代表能连
   `opencode.ai`（网关真正的上游）。抽样 30 个 https 代理访问
   `https://opencode.ai/zen/v1/models`，有 5 个超时/连不上，却仍被当成
   https 交付。
2. **每个代理复核要发 5～6 次请求**：http 回声 + baidu reality + https +
   匿名性 + 篡改 + 单独测延迟。160 个代理每分钟全量复核 ≈ 1000 次请求，
   把免费代理和目标站都打出限流，反而制造大量「假死」。
3. **水位目标不可达**：global/all=1000、stable1=400、safe=100，而实际池子
   只有 160 左右、safe 长期 2 个。调度器每 5 分钟跑 2 轮、每轮验证 2000 个
   候选，永远补不满，持续占用出口和验证资源。
4. **复核是「全量每分钟」**：池子越大，复核负载越高，形成负反馈。

参考 jhao104/proxy_pool 的做法：验证器只做少量必要请求、目标可配置、
检查按批/按分数滚动，而不是全量高频轰炸。我们按这个方向改。

## 完成内容

### 1. https 验证目标改成真实上游

`helper/check.py`：

- `HTTPS_URL` 默认改为 `https://opencode.ai/zen/v1/models`
  （可用 `HTTPS_CHECK_URL` 覆盖）。
- 判定标准从「返回体必须是纯 IP」改成「拿到业务响应即可」：
  `200/401/403/429` 都算 CONNECT + TLS + 目标可达；5xx/超时/连接错误不算。
- 这样 `use_proxy:https` 的含义变成「网关真正能访问的 HTTPS 代理」，
  而不是「能访问 3322 的代理」。

### 2. 每个代理的复核请求 5～6 次 → 2 次

- 去掉额外的 baidu `reality` 请求（HTTP 回声本身已校验返回体是合法 IP）；
  需要时用 `REALITY_CHECK=1` 打开。
- 匿名性/篡改探针默认关闭（`PROBE_SAFETY=1` 才开）：网关只用 https+延迟，
  不需要安全标签。
- 延迟直接复用 HTTPS 目标请求的 TTFB，不再单独发一次 latency 请求。
- 同步 `check()` 路径也记录 `last_time`，为滚动复核提供排序依据。

### 3. 复核改成滚动批次

`helper/scheduler.py` + `handler/proxy_service.py`：

- 复核周期 1 分钟 → **3 分钟**。
- 每次只复核 **100 个**（`CHECK_BATCH_LIMIT`），按「上次失败优先、
  上次复核时间最旧优先」取，几轮覆盖全池。
- 池子 200+ 时不再每分钟发上千请求。

### 4. 水位改到现实值 + 新增 https 维度

`config/services.py`：

| 服务 | 旧目标 | 新目标 |
|---|---|---|
| cn/all | 100 | 40 |
| cn/https | — | 10 |
| global/all | 1000 | 200 |
| global/https | — | 60 |
| global/safe | 100 | 0（安全探针默认关） |
| global/stable1/2/3 | 400/200/100 | 100/50/25 |

`service_levels()` 支持 `https` 服务：直接统计「该区域且 https=true」的数量，
这是网关真正消费的维度。`RedisPool.count_by_region()` 增加 `https_only`。

### 5. refresh 可观测

每轮补水打印：候选数、实际验证数、通过数、新增数、其中 https 数。方便判断
是「源没货」还是「验证通过率低」。

## 技术决策及理由

1. **验证目标必须等于业务目标**：代理池的 https 标记如果只验证一个无关的
   小站，交付给网关的候选就会大量在真实上游超时。改成 opencode.ai 的
   models 端点后，https 池数量略降，但「标记为 https 就能连上游」。
2. **少发请求比多验证更重要**：免费代理和目标站都怕高频。把每个代理的
   5～6 次请求压到 2 次，吞吐提升的同时减少误杀和限流。
3. **滚动复核而不是全量**：池子越大全量越不可持续。按 last_time 滚动，
   最坏情况下一个代理 2～3 个周期被复核一次，免费代理寿命分钟级也够用。
4. **水位要可达**：不可达的水位会让调度器永远在补源，反而挤占复核和正常
   供给。把目标降到「当前源和通过率能维持」的量级，并新增 https 目标，
   让补源有的放矢。
5. **不把 zen 探测搬进代理池**：zen free 档的 IP 滥用判定是网关业务，
   需要 opencode 的头/body 和模型名；代理池只负责「HTTPS + 目标可达」，
   避免两个项目重复探测、互相耦合。

## 踩坑记录

- **https 不等于可访问 opencode.ai**：抽样发现部分 https 代理访问 3322 正常、
  访问 opencode.ai 直接 ReadTimeout/ConnectError。只改验证目标就能提前剔除
  这些「假 https」。
- **复核负载会反噬池子**：全量每分钟复核 + 每代理 5～6 请求，会把还能用的
  代理打成失败，`fail_count` 累积后被淘汰，看起来像「代理突然全死了」。
- **safe 水位是无效目标**：免费源里 elite+未篡改长期只有 2 个，100 的目标
  永远达不到，却每轮都触发补源。改成 0 后调度器终于能专注 all/https。
- **测试 `test_probe::test_tamper_clean` 有模块级缓存串扰**：前一个用例把
  `_DIRECT_HASH` 缓存成别的值，后一个用例断言失败；在用例里重置缓存即可，
  与本次业务改动无关但顺手修了。

## 下一步

1. 观察 1～2 小时，确认 global/all、global/https 能稳定在水位附近，不再
   无限补源。
2. 网关侧可直接读 `use_proxy:https` 集合（或 Redis hash 里 `https=true` 的
   字段）作为候选，少探测 2/3 的无效代理；候选质量也会更高。
3. 若 https 仍不够，再扩源（住宅/轮换出口）；zen 的 IP 滥用判定只能靠更多
   干净出口解决，代理池无法逆向。
