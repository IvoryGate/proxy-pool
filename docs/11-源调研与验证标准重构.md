# 阶段 11：源调研、验证标准重构、抽样与 stable 分级

## 背景思考

用户给出了一份全网免费代理源调查汇总,希望系统化补源。期间用户反复质疑:
"结论怎么一会儿 global 达标、一会儿 cn 达标,始终没都达标?"——这个问题
点破了我们**验证标准的反复横跳**,也让我们最终定位并修复了根因。

## 完成内容

### 1. 新源接入(实测评估)
- **databay**(`fetcher/sources/databay.py`):免费无 key API,JSON 带
  ip/port/iso/ssl/anonymity/latency。支持 `anonymity=elite` 定向(补 safe)。
- **free-proxy-list**(`fetcher/sources/free_proxy_list.py`):HTML 表格,
  带 region/anonymous/https 元数据;主列表 + anonymous 高匿专页。
- **openproxylist**(`fetcher/sources/openproxylist.py`):GitHub 仓库,
  必须走 jsdelivr CDN(raw.githubusercontent 被墙)。
- **proxyscrape 增强**:官方 API + jsdelivr JSON 双通道。
- **hproxy 默认定向 CN**:全量 2 万+ 可用率 ~10%,定向 CN 才有质量。

### 2. 验证标准重构(核心,回答"反复横跳")
反复横跳的根源是**换了 3 次验证目标,每次引入新缺陷**:
1. youtube/baidu 分流 → youtube 被墙,**误杀境外真代理**
2. 换 ipify(纯 IP 回显)→ **太宽松,收进 Cloudflare 假代理/劫持代理**
3. 换 baidu 但内容校验还写"要纯 IP" → **误杀所有 baidu 响应**

最终修复(`helper/check.py`):
- **ipify 存活验证**(校验返回体是纯 IP → 拦劫持代理)
- **baidu 真实转发**(第二道,确认代理真转发流量 → 拦 Cloudflare 假代理)
- **baidu+https 并行检测**:慢代理从串行 3×timeout 降到 ~timeout,实测提速 3-28 倍
- `CHECK_BATCH_SIZE` 500(1000 吞吐高但部分代理被限流误杀)

### 3. 水塘抽样(大源随机抽样)
- `fetcher/util.py::reservoir_sample`:流式等概率抽 k 个,内存 O(k)。
- manager 对每个源抽样(替代"取前 N 个"),避免大源反复取同一批。
- 加 `max_scan=5000` 限制扫描量:水塘抽样需遍历全流(2 万+),限制后
  hproxy 抽 300 从几十秒降到 4s,且两次抽 50 重叠 0。

### 4. region 探测(补 CN 分桶)
- `helper/region_detect.py`:ip-api.com 批量反查代理 IP 归属地。
- 纯文本源(hproxy/ip3366)不带 region,入库后被错分 global;
  现在 refresh 入库前对空 region 代理补打标签。

### 5. stable 分级(stable1/2/3)
- `config/services.py`:`STABLE_LEVELS = {stable1:1, stable2:3, stable3:5}`
  (score 下限)。SERVICE_MIN 里 stable 拆成三档。
- `db/redis_client.py`:`count_by_region` 加 `min_score` 参数。
- `handler/proxy_service.py`:service_levels/get 支持档位,`stable` 兼容=stable1。
- 好处:业务更精细(轻任务用低档、重任务用高档)、池子利用率高、
  水位更能反映真实健康度。

### 6. 稳定性/容错调整
- `MAX_FAIL_COUNT` 3→5:免费代理波动大,3 次连续失败易误删活代理。
- 调度器频率:补源 10→3 分钟、复核 2→1 分钟(免费代理分钟级短命,
  需"边漏边补")。

### 7. 测试隔离修复(重要)
- `tests/test_redis_client.py` 的 `make()` 调 `pool.clear()` **清空了生产
  Redis 池**(db=0)!这是池子一度归零的元凶。改为测试用独立 db=15。

## 技术决策及理由

1. **双保险验证目标**而非单目标:ipify(内容可校验)负责拦劫持,
   baidu(真实网站)负责确认转发,两者互补缺一不可。
2. **水塘抽样而非随机截断**:只需遍历流(受 max_scan 限制),每个候选
   等概率,兼顾"样本多样"与"不读完整大源"。
3. **stable 用 score 下限而非布尔**:score 是累计信任(成功+1失败-1),
   天然适合分档;比"是否 stable"信息量大。
4. **探针复用验证时的 AsyncClient**:不再每代理重建连接,匿名+篡改并行,
   全池复核从 24 分钟降到 ~1 分钟内。

## 踩坑记录

- **坑 1(最重)**:测试污染生产库——`test_redis_client.make()` 里
  `pool.clear()` 直接清 db=0。教训:**测试必须用独立 db**,生产数据隔离。
- **坑 2**:验证目标反复横跳。每换一次目标,池子统计就"反转"一次,
  用户一度怀疑判断标准。教训:验证目标必须**稳定可达 + 能拦假货**,
  且改目标必须同步改配套的内容校验。
- **坑 3**:水塘抽样要遍历全流,大源(2 万+)很慢。加 max_scan 限制。
- **坑 4**:并发太高(batch 1000+)导致部分代理被瞬时限流误杀。
- **坑 5**:调度器复核时 CN 代理大面积"死亡"其实是真死(免费 CN 寿命分钟级),
  不是误删——验证器淘汰逻辑本身正确。
- **坑 6**:`PYTHONPATH=.` 必须与 `nohup` 同命令前缀,漏了会 import 失败
  立即退出。

## 关键结论

- **免费 CN 代理稀缺且分钟级短命**:一轮 refresh(139s)只补 1 个 CN,
  靠免费源**无法稳定维持 cn/all 30 水位**。这是源质量上限,非系统缺陷。
  → 已接受现状,后续专项找 CN 源。
- **境外代理相对稳定**:databay/free-proxy-list/proxyscrape 持续供给,
  global 各层(含 stable3)可长期维持。
- **系统是健康的**:验证、探针、水位、调度、API 语义取用全部正常,
  当前 global 六层全达标。
- **测试隔离 + 稳定验证目标**是本阶段最重要的工程收益。
