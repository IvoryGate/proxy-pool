# 阶段 15：全球大源接入与补源提速

## 背景思考

网关（poverty-gateway）那边可用代理长期不足（usable 39/60，冷区 77），
候选可用率仅 ~10%。排查后确认根因是 **proxy-pool 池子本身太小**（~200 个），
源少 + 抓取慢 + 补源 job 卡死导致池子缩水。

用户方向：**全网补源，接入更多全球免费代理源**，让池子变大，网关才有
足够候选去筛 zen 可用 IP。

## 完成内容

### 1. 接入 6 个全球大源（~7700 候选）

| 源 | 文件 | 候选数 | 说明 |
|---|---|---|---|
| TheSpeedX http | `thespeedx.py` | 2625 | GitHub 超大 HTTP 列表 |
| ShiftyTR | `shiftytr.py` | 823 | HTTP/SOCKS 混合 |
| jetkai | `jetkai.py` | 1801 | 在线代理库 http |
| sunny9577 | `sunny9577.py` | 1598 | GitHub Pages 聚合 |
| monosans | `monosans.py` | 458 | 干净代理列表 http |
| clarketm | `clarketm.py` | 400 | 已验证列表 raw |

全部走 `fetcher/util.py::fetch_text()` 双通道抓取（见下）。

### 2. 双通道抓取 fetch_text（核心基建）

`fetcher/util.py` 新增 `fetch_text()`：
- **raw 通道**：短超时快速失败（connect 5s / read 8s），抖了就换
- **jsdelivr 兜底**：稳定 CDN，自动把 raw URL 转 `@branch` 格式
- 踩坑：**raw→jsdelivr 转换缺 `@branch` 导致 404**（实测 `cdn.jsdelivr.net/gh/user/repo/path` 返回 404，必须有 `@master`/`@main`）

### 3. 抓源提速（5x）

- **并行抓源**：`fetcher/manager.py::run()` 用 `ThreadPoolExecutor(max_workers=8)`
  每源独立线程抓取。总耗时从"所有源之和"变成"最慢源"。
  实测：串行 90s+ → 并行 17s（1737 个）。
- **取前 N 替代水塘抽样**：`max_per_source` 时用 `itertools.islice` 直接取前 N，
  不再 `reservoir_sample`（水塘要遍历全流，对 7600 条大源很慢）。
- **connect 超时**：`BaseFetcher._http_get` 和 `Checker` 的 timeout 都拆
  connect/read。只设 read 时死代理连接会被内核 TCP 拖 30s+。

### 4. 验证提速

- `refresh` 验证前先按 `pool.exists` 过滤，只验证真正的新 IP
  （大批量抓取时大量重复/已存在，跳过省时间）。
- `Checker.__init__` timeout 拆 connect=2s。

### 5. 补源 job 防卡死（关键）

根因：一轮 refresh 40-80s，`MAX_WATERLINE_ROUNDS=4` → 最坏 4×80=320s
跑不完 3 分钟调度周期，水位 job 永久被 skip（`maximum number of running
instances reached`），补源严重滞后，池子缩水。

修复（`config/services.py`）：
- `MAX_WATERLINE_ROUNDS` 4→2、`MAX_STALL_ROUNDS` 3→2
- `MAX_PER_SOURCE` 300→120
- 效果：2 轮内快速返回，每周期都能补源。日志恢复正常打印
  `补源 2 轮后仍未达标`。

## 技术决策及理由

- **jsdelivr 而非 raw 直连为主**：服务器直连 raw.githubusercontent 抖动
  （实测 1s~60.8s 不定），jsdelivr 稳定（0.6-1.8s）。
- **不接入 SOCKS 源**（TheSpeedX socks4 / hooksie）：池子验证只走 HTTP，
  socks 代理会被判死，浪费抓取。
- **保留慢源**（free-proxy-list/geonode/proxyscrape）不删：它们有独特数据，
  靠并行抓取 + 超时兜底不拖累整体。

## 踩坑记录

1. **raw→jsdelivr 缺 @branch 404**：`cdn.jsdelivr.net/gh/user/repo/path`
   是 404，必须 `@master` 或 `@main`。
2. **connect 超时陷阱**：httpx 单值 `timeout=8` 只约束 read，连接卡住时
   内核 TCP 拖 30s+。必须 `httpx.Timeout(8, connect=5, read=8, ...)`。
3. **水塘抽样拖慢大源**：reservoir_sample 要遍历全流（max_scan=5000）才
   等概率取样，对 7600 条大源等于全遍历，抓取从秒级变分钟级。
4. **补源 job 周期超时**：轮数不限制时单次 job 跑 320s+，APScheduler
   max_instances=1 导致后续周期永久 skip，这是池子缩水的隐藏元凶。
5. **LSP 误报 httpx 未解析**：宿主机无 Python 依赖，IDE 报错但不影响
   Docker 运行。

## 阶段 15 后续 fix（补源稳定性收尾）

阶段 15 之后还有几个与补源相关的收尾改动，一并记录：

### 1. 补源轮数调低，防 job 卡死调度周期

`config/services.py`：
- `MAX_WATERLINE_ROUNDS` 4→2、`MAX_STALL_ROUNDS` 3→2
- `MAX_PER_SOURCE` 300→120

原因：单轮 refresh（抓取+验证）40-80s，4 轮最坏 320s+，跑不完 3 分钟
调度周期 → 水位 job 被 `max_instances=1` 永久 skip，补源严重滞后（日志
只看到"复核"、没有补源结果）。调低后 2 轮内快速返回，每周期都能补源。

### 2. 抓源跟随重定向 + 提高每源抓取量

- `BaseFetcher._http_get` 加 `follow_redirects=True`：部分源（如
  google-proxy）返回 301 需重定向到 https，之前不跟随导致抓空。
- `MAX_PER_SOURCE` 120→250（240→？）：主要大源（thespeedx/jetkai/
  monosans/databay）候选质量不错，提高抓取量贡献更多候选。验证仍是
  瓶颈，250 在可接受范围。

### 3. 后续搜源结论（复盘）

继续全网搜源测试 40+ 候选源后，结论是**免费 HTTP 代理源已基本挖掘殆尽**：
- `mishakorzik/Free-Proxy`（百万条）：看着壮观但**可用率 0%**（纯垃圾
  灌水），实测抽样 100 个验证 0 通过，已移除。
- `sslproxies / us-proxy / google-proxy`（free-proxy-list 系列）：宿主机
  可达但 **scheduler 容器内网络不可达**（Network unreachable），接不了。
- 已接入的 18 源中 `databay / monosans / thespeedx-http / proxyscrape`
  是质量主力，继续加源边际收益极低。

**最终水位**：池子 ~292（可用 ~133+），相比阶段 15 启动时的 216 明显
扩大，网关侧也从补源受益（候选 pool_size 77→99→持续的 zen 可用提升，
见网关阶段 14 文档）。
